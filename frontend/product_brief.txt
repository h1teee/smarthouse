# Техническое задание (Бриф) для Backend-разработки: SmartHome V2

## 1. Описание системы
SmartHome V2 — платформа для взаимодействия жителей и управляющих компаний (УК), обогащенная функциями искусственного интеллекта.
Система использует клиент-серверную архитектуру (мобильное PWA-приложение + Backend API). 
Бэкенд должен обеспечивать обработку запросов, хранение данных, интеграцию с внешними сервисами (SMS, AI) и отдавать данные в формате JSON (REST API или GraphQL).

---

## 2. Основные сущности БД (Модели данных)

1. **User (Пользователь)**
   - Поля: id, phone, role (RESIDENT | UK_MODERATOR), push_token, created_at.
2. **Address / House (Адрес / Дом)**
   - Поля: id, city, street, building, latitude, longitude, uk_id (привязка к УК).
   - Статусы дома (для карты): water_status, electricity_status, heating_status, gas_status (OK | OUTAGE | PLANNED_MAINTENANCE).
3. **Apartment (Квартира)**
   - Поля: id, house_id, number.
4. **UserAddress (Привязка пользователя к квартире)**
   - Поля: user_id, apartment_id, is_verified.
5. **UtilityAccount (Лицевой счет)**
   - Поля: id, account_number, user_id, provider_name.
6. **Bill (Квитанция ЖКХ)**
   - Поля: id, account_id, period (месяц/год), total_amount, pdf_url, raw_data (JSON с детализацией), ai_analysis_summary.
7. **IncidentRequest (Заявка / Инцидент)**
   - Поля: id, author_id, house_id, image_url, ai_category, ai_description, status (PENDING | IN_PROGRESS | RESOLVED | REJECTED), priority, created_at.

---

## 3. Существующий функционал (API Endpoints)

### 3.1. Auth API
- `POST /api/auth/send-code` — отправка SMS-кода.
- `POST /api/auth/verify` — проверка кода, выдача JWT/Refresh токенов.

### 3.2. Address & Account API
- `GET /api/address/search` — геокодирование, поиск адреса по строке.
- `POST /api/user/address` — привязка адреса к профилю жителя.
- `POST /api/user/account` — привязка лицевого счета.

### 3.3. Requests & Feed API (Для жителя)
- `GET /api/feed/house/{houseId}` — получение ленты новостей и активных заявок (отключений) по дому.
- `POST /api/requests/upload-photo` — загрузка фото проблемы (сохранение в S3, вызов AI Vision сервиса).
- `POST /api/requests/ai-recognize` — анализ фото (возвращает категорию и сгенерированный текст проблемы).
- `POST /api/requests/submit` — финальная отправка заявки жителем после превью.

### 3.4. Bills API (Счета ЖКХ)
- `GET /api/bills` — получение списка квитанций по лицевому счету пользователя.
- `GET /api/bills/{billId}/ai-analysis` — запрос к LLM на формирование текстового объяснения начислений, сравнение с прошлым месяцем.

### 3.5. UK Moderation API (Для сотрудников УК)
- `GET /api/uk/requests` — список всех входящих заявок со статусом PENDING.
- `PATCH /api/uk/requests/{id}/status` — обновление статуса заявки (принять в работу, отклонить, объединить дубликаты).
- `POST /api/uk/announcements` — создание глобального уведомления (например, о плановом отключении воды), которое попадет в Feed всем жителям дома.

## 4. НОВЫЙ ФУНКЦИОНАЛ: Интерактивная карта (Map API)

Бэкенд должен обеспечить данные для отображения глобальной карты с домами и их текущим статусом.

### 4.1. Логика работы
У каждого дома (сущность `House`) должны вычисляться глобальные статусы (Свет, Вода, Тепло). Статусы зависят от активных `IncidentRequest` или объявлений УК, привязанных к этому `house_id`.
Например, если по дому заведена и подтверждена заявка "Авария на подстанции", статус `electricity_status` меняется на `OUTAGE`.

### 4.2. Endpoints для карты
- `GET /api/map/houses?bbox={lat1,lon1,lat2,lon2}` 
  - **Описание**: Получение списка домов в видимой области экрана (Bounding Box).
  - **Ответ**: Массив объектов `{ houseId, lat, lng, statuses: { water, electricity, heating } }`.
  - **Оптимизация**: При большом отдалении (зуме) можно использовать кластеризацию на стороне БД (PostGIS).

- `GET /api/map/houses/{houseId}/status`
  - **Описание**: Получение детальной информации о конкретном доме при клике.
  - **Ответ**: Текущие статусы ресурсов, список активных аварий (название, ожидаемое время починки), обслуживающая УК.

## 5. Интеграции и AI-стек (Требования)
1. **Хранилище файлов**: S3 (MinIO / AWS) для хранения фотографий заявок и PDF-квитанций.
2. **База данных**: PostgreSQL (рекомендуется использование PostGIS для работы с координатами карты).
3. **AI Vision (Распознавание проблем)**: Интеграция с GPT-4o / Claude 3.5 Sonnet / YandexGPT Vision для анализа фотографий, извлечения текста и классификации проблемы.
4. **AI Text (Анализ квитанций)**: Промпт-инжиниринг через LLM API. Бэкенд должен передавать JSON-структуру квитанции за текущий и прошлый месяц и получать user-friendly объяснение.
5. **Пуш-уведомления**: Интеграция с Firebase Cloud Messaging (FCM) / APNs для уведомлений о смене статуса заявки и авариях.

## 6. НОВЫЙ ФУНКЦИОНАЛ: Система «Партнеры и Привилегии»

### 6.1. Суть фичи
В профиле пользователя выводится горизонтальная карусель партнерских офферов (СБП, ВкусВилл, Яндекс и т.д.). Офферы могут быть как глобальными (федеральными), так и локальными (конкретно для данного ЖК). 
Главное условие: доступ к офферам должен быть привязан к финансовой дисциплине жителя (например, оффер доступен только если `debt == 0`).

### 6.2. Необходимые таблицы в БД (Сущности)
Для гибкого управления витриной через админку УК понадобятся 2 сущности:
1. **Partners** (Партнеры): `id`, `name`, `logo_svg_url`, `brand_color_hex`
2. **Offers** (Офферы): `id`, `partner_id`, `badge_text` (например, "Федеральный" или "Для вашего ЖК"), `offer_text` (описание акции), `promo_code` (или `action_link`), `is_active`, `conditions` (jsonb, например `{"requires_zero_debt": true}`).

### 6.3. Логика на стороне Бэкенда (Endpoint)
- **Метод:** `GET /api/v1/profile/privileges`
- **Что делает бэкенд при вызове:**
  1. Идет в биллинг и проверяет текущий баланс пользователя (есть ли задолженность за прошлые месяцы).
  2. Достает из базы активные офферы `Offers` (где `is_active = true`).
  3. Если у оффера стоит `requires_zero_debt: true`, а у юзера есть долг, бэкенд отдает этот оффер со статусом `isLocked: true` (фронтенд повесит на него замочек и серый фильтр) либо вообще не отдает в массив (на усмотрение бизнеса).

### 6.5. Дальнейшее развитие
